# 修复资源受限的 DAG 调度器

这是一个真实代码修复任务。graph.py、scheduler.py、report.py 是带缺陷的初始实现，不是正确算法。请理解需求，修复实现，实际运行测试，并说明算法及复杂度。不要为了通过测试修改测试、删除断言或硬编码测试结果。

## 文件与接口

- model.py：不可变 Task 和 Run 数据结构，保持接口不变。
- graph.py：prepare(tasks, slots, memory) 返回 (by_id, order, rank)。
- scheduler.py：schedule(tasks, slots=2, memory=4) 返回 Run 列表。
- report.py：summarize 返回统计字典。
- tests/test_scheduler.py：18 个测试方法，包含多组非法输入和 30 个固定种子随机 DAG。

## 图与合法性

任务 ID 必须是非空字符串且唯一；每个依赖必须存在，不能重复、自依赖或形成环（包括不连通分量中的环）。duration、任务 memory、slots、总 memory 都必须是正整数，bool 不算整数；单个任务的 memory 不得超过总量。非法输入统一抛 ValueError，即使任务列表为空，也必须验证全局容量。

order 是稳定的拓扑序：每一步从入度为零的剩余任务中选择 ID 字典序最小者。rank 是从该节点出发到任意终点的最长路径时长，包含自身 duration。实现不能依赖输入顺序，也不能修改输入列表。1200 层依赖链不能触发 Python 递归限制。

## 调度策略（是确定性贪心策略，不要求全局最优）

时间从 0 开始。每个运行任务占一个 slot 和自身声明的 memory，不可抢占。

在每个事件时间：先同时完成所有 end 等于当前时间的任务并释放资源，再计算所有依赖已完成的未启动任务。就绪任务按 rank 降序、ID 字典序升序排序；依次尝试启动能放入剩余资源的任务。某任务内存放不下时跳过它，继续考虑后面的任务；slot 用完后不再启动。当无法再启动任务时，直接跳到下一个完成时间，不允许逐整数时刻循环。

返回值按 (start, id) 排序。相同时间的完成先于启动，区间语义是 [start, end)。必须支持 10**12 的时长和空图。

## 统计

makespan 是所有任务的最大 end（空图为 0）；busy_time 是所有 duration 之和；peak_memory 是任意时刻实际并行占用的最大内存，不能把所有任务内存直接相加。runs 按调度器输出顺序序列化。
